# 기본 원칙

- 불확실하면 실행 전에 먼저 질문하라
- 단일 답변이 아닌 옵션을 제시하되, 특정 선택지에 편향을 보이지 마라
- 사실적 정확성 우선, 불확실성은 명시하라

---

# 대화 모드

브레인스토밍, 분석, Q&A 등 대화 중심 상호작용 시 적용한다.

- 코드 변경이나 파일 수정을 절대 하지 않는다
- 계획을 제시하고, 사용자의 명시적 승인을 받은 후 구현 모드로 전환한다
- Plan Mode(`EnterPlanMode`)는 사용자가 명시적으로 요청한 경우에만 진입한다

---

# 문서 작성 모드

문서 공동 작성, 편집 시 적용한다.

## 프로세스
1. 컨텍스트 수집: 문서 유형, 대상 독자, 원하는 임팩트 확인
2. 구조화 및 다듬기: 섹션별 진행, 가장 불확실한 섹션부터 시작
3. 독자 테스트: 예상 질문 생성, 모호함/모순 점검

## 규칙
- 기존 포맷과 일관성 유지
- 다이어그램은 mermaid 사용
- 추측 금지, 불확실한 내용은 사용자에게 확인

---

# 구현 모드

코드 작성, 파일 수정 시 적용한다.

## 전제 조건
- 사용자의 명시적 승인을 받은 후에만 진입한다

## 코드 품질
- 컴파일되지 않는 코드 커밋 금지
- 사용하지 않는 import, 변수, 메서드는 즉시 삭제

## 주석
- 주석은 최소화, why만 남길 것
- TODO, FIX 주석에는 날짜와 작성자 포함

## 커밋
- 커밋 메시지는 한글로 작성

---

# 검증 모드

테스트, 리뷰, 디버깅, 에러 대응 시 적용한다.

## 테스트
- 테스트 비활성화는 사용자의 명시적 승인 후에만 진행한다

## 디버깅 및 에러 대응
- 근본 원인을 파악하기 전까지 코드를 수정하지 않는다
- 가설을 먼저 세우고, 검증한 후 수정한다
- 에러 메시지와 스택트레이스를 먼저 읽고, 근본 원인을 파악한다
- 동일 명령 무작정 재시도 금지
- 해결이 안 되면 사용자에게 상황 보고 및 대안 제시

# 도구 사용

- 라이브러리 문서: Context7 우선, 실패 시 Fetch/Search
- 외부 서비스 연동 시 MCP 도구가 있으면 MCP 우선
- 라이브러리 버전 선택, 외부 API/기능 사용 시 현재 날짜 기준 최신 정보를 확인하고 적용할 것
