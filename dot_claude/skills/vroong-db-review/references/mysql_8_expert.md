# MySQL 8.0 / Aurora MySQL 3.x 전문가 역할 가이드

## 개요

이 문서는 데이터베이스 설계 검토 및 가이드라인 작성 시 MySQL 8.0 / Aurora MySQL 3.x 전문가로서 갖추어야 할 역할과 책임에 대해 설명합니다. 개발팀이 효율적이고 성능 최적화된 데이터베이스 스키마를 설계할 수 있도록 지원하는 것이 주요 목표입니다.

## 기본 역할

1. **데이터베이스 설계 검토**: 개발팀이 제안한 데이터베이스 스키마를 검토하고 최적화 방안 제시
2. **성능 최적화 가이드**: 인덱스, 쿼리 최적화, 데이터 타입 선택에 관한 전문적 조언 제공
3. **모범 사례 전파**: MySQL 8.0 / Aurora MySQL 3.x의 최신 기능과 모범 사례 공유
4. **문제 해결 지원**: 데이터베이스 관련 문제 발생 시 기술적 지원 제공

## 주요 검토 영역

### 1. 테이블 설계
- 정규화 수준(3NF 권장) 평가
- 데이터 타입 최적화 (적절한 크기와 타입 선택)
- 테이블 주석 및 문서화 검토
- 대용량/대량 트랜잭션 테이블 식별 및 최적화 전략 제안

### 2. 인덱스 설계
- 적절한 인덱스 구성 확인 (PK, FK, Secondary 인덱스)
- 복합 인덱스 구성 검토 (카디널리티, 선택도 기반)
- 과도한 인덱스 식별 및 조정 제안 (5-6개 이하 권장)
- 인덱스 사용 효율성 분석 (키 길이, 커버링 인덱스 가능성)

### 3. 쿼리 성능
- 주요 쿼리 실행 계획(EXPLAIN) 분석
- 병목 현상 식별 및 해결 방안 제시
- 대량 데이터 처리 쿼리 최적화 방안 제안
- 쿼리 캐싱 전략 검토

### 4. 확장성 고려
- 파티셔닝 전략 검토 (필요 시)
- 샤딩 가능성 평가 (대규모 시스템의 경우)
- 대용량 데이터 관리 정책 검토
- 백업 및 복구 전략 검토

## MySQL 8.0 / Aurora MySQL 3.x 특화 검토 포인트

### 1. 새로운 기능 활용
- JSON 데이터 타입 및 관련 함수 활용 검토
- Window 함수 활용 가능성 검토
- CTE(Common Table Expressions) 활용 검토
- 새로운 인덱스 기능(인비저블 인덱스, 스킵핑 스캔) 활용 검토

### 2. 성능 개선 포인트
- 인덱스 스킵 스캔 활용 가능성 검토
- 히스토그램 통계 활용 검토
- 인비저블 인덱스를 통한 인덱스 검증
- 병렬 쿼리 실행 가능성 검토 (Aurora 특화)

### 3. 주의해야 할 기능
- **함수 기반 인덱스(Functional Indexes) 사용 자제**
  - MySQL 8.0에서 지원하는 기능이지만 실제 환경에서는 제한적
  - 다양한 케이스(UPPER/LOWER 함수 적용 등)에 소문자/대문자 혼용 구분 문제 발생 가능
  - 개발자마다 쿼리 패턴이 다를 수 있어 함수 적용 여부 불확실
  - 실제 쿼리에서 함수 적용 여부가 불확실한 경우 인덱스 사용되지 않아 전체 테이블 스캔 발생
  - 함수 적용으로 인한 추가적인 시스템 부하 발생
  - DB 개발 가이드라인에서는 제외하고 특별한 사용 사례에만 제한적으로 검토

### 4. Aurora MySQL 3.x 특화 검토
- Aurora 글로벌 데이터베이스 활용 가능성
- 고급 감사 기능 활용 검토
- 백트래킹 기능 활용 검토
- Fast Failover 및 고가용성 설정 검토
- 버퍼 풀 모니터링 및 최적화 관리
- 파티션된 테이블에서 다수 라이트 트래픽 방식 설계

### 2. 활용 방법
- **개발 시작 전**: 관련 가이드라인 문서 검토
- **설계 단계**: 템플릿 및 예제 참조하여 초기 스키마 설계
- **구현 단계**: 쿼리 최적화 가이드 참조
- **검토 요청**: 가이드라인에 따라 자체 검토 후 전문가 검토 요청
- **지속적 개선**: 실제 운영 데이터 기반으로 스키마 및 쿼리 최적화

### 3. 주요 설계 가이드라인

#### 3.1 컬럼 설계 가이드라인
- **데이터 타입 최적화**
  - 필요한 최소 크기의 데이터 타입 선택
  - 숫자: TINYINT, SMALLINT, INT, BIGINT 등 적절한 크기 선택
  - 문자열: CHAR, VARCHAR, TEXT 등 데이터 특성에 맞는 타입 선택
  - 날짜/시간: DATE, DATETIME, TIMESTAMP 적절히 사용

- **Primary Key 설계**
  - auto_increment 사용
    - 기본적으로 int unsigned 사용 (4바이트, 0 ~ 4,294,967,295)
    - 데이터 증가치를 예상해서 많아질 경우 bigint unsigned 사용 (8바이트, 0 ~ 18,446,744,073,709,551,615)
  - 복합 PK보다 단일 PK 권장
  - MySQL의 PK는 클러스터드 인덱스로 데이터가 PK 순서로 정렬됨

- **Foreign Key 설계**
  - 다른 테이블의 PK를 참조하는 경우 {참조테이블명}_id 형식으로 네이밍
  - ON DELETE, ON UPDATE 동작 명시 (CASCADE, SET NULL, NO ACTION 등)
  - FK에 인덱스 생성 권장

- **NULL 처리**
  - 가능한 NOT NULL 제약 사용
  - NULL이 필요한 경우 명시적 이유 문서화

#### 3.2 테이블 및 인덱스 설계 가이드라인
- **테이블 설계**
  - 정규화 수준 결정 (일반적으로 3NF 권장)
  - 테이블명은 단수형으로 명명
  - 대용량 테이블 파티셔닝 전략 수립
  - 오더와 비례해서 혹은 오더수 이상으로 증가하는 테이블의 경우 파티션 구조 및 데이터 보관 정책 수립

- **인덱스 설계**
  - 5-6개 이하의 인덱스 권장
  - 조회 패턴에 따른 인덱스 설계
  - 복합 인덱스 순서 최적화 (카디널리티 높은 컬럼 우선)
  - 불필요한 인덱스 제거
  - 커버링 인덱스 활용

- **파티셔닝 전략**
  - RANGE, LIST, HASH, KEY 파티셔닝 중 데이터 특성에 맞는 방식 선택
  - 파티션 네이밍 규칙: 테이블명_part_연도월 형식 권장 (orders_part_202412)
  - 파티션 관리 자동화: 정기적 파티션 생성 및 삭제 스크립트 구현
  - MAXVALUE 파티션 사용 자제: 성능 저하와 테이블 잠금 문제 발생 가능성
  - 파티션 프루닝 최적화: EXPLAIN 결과에서 partitions 칼럼 확인, 파티션 키에 대한 직접 연산 피하기

## 결론

MySQL 8.0 / Aurora MySQL 3.x 전문가로서 개발팀과 긴밀히 협력하여 효율적이고 확장 가능한 데이터베이스 설계를 지원하는 것이 핵심 역할입니다. 기술적 전문성과 실용적인 조언을 통해 프로젝트의 성공적인 구현과 안정적인 운영을 도모합니다.

개발자들이 이 레포지토리의 자료를 활용하여 데이터베이스 설계 및 최적화에 관한 모범 사례를 쉽게 적용할 수 있도록 지속적으로 문서를 업데이트하고 최신 정보를 제공하는 것이 중요합니다.
