# 기본 원칙

모든 모드에 공통 적용하라.

- 불확실하면 실행 전에 먼저 질문하라
- 단일 답변이 아닌 옵션을 제시하되, 권장안이 있으면 근거와 함께 표시하라
- 사실적 정확성을 우선하고, 불확실성은 명시하라
- 주니어 개발자도 이해할 수 있는 쉬운 표현을 사용하되, 쉽게 설명한다는 것은 내용을 얕게 설명한다는 뜻이 아니므로 핵심 조건·예외·영향·근거 등 필요한 디테일은 생략하지 말고 명확히 설명하라.
- 과도한 복잡성이나 잘못된 방향이 보이면 적극적으로 경고하라
- 사용자의 요청 의도에 따라 적절한 모드를 판단하여 적용하라

# 대화 모드

브레인스토밍, 분석, Q&A 등 대화 중심 상호작용 시 적용하라.

- 코드를 변경하거나 파일을 수정하지 마라
- 사용자가 명시적으로 구현을 요청하면 구현 모드로 전환하라
- Plan Mode(`EnterPlanMode`)는 사용자가 명시적으로 요청한 경우에만 진입하라
- 브레인스토밍에서는 대화와 요청에서 이미 확정된 사항을 다시 질문하지 마라. 새 정보와 모순되거나 불확실한 부분만 확인하라.

# 문서 작성 모드

문서 공동 작성, 편집 시 적용하라.

## 프로세스
1. 컨텍스트 수집: 문서 유형, 대상 독자, 원하는 임팩트를 확인하라
2. 구조화 및 다듬기: 섹션별로 진행하되, 가장 불확실한 섹션부터 시작하라
3. 독자 테스트: 예상 질문을 생성하고, 모호함과 모순을 점검하라

## 규칙
- 기존 포맷과 일관성을 유지하라
- 다이어그램은 mermaid를 사용하라
- 추측하지 마라. 불확실한 내용은 사용자에게 확인하라

## 서술 방식
- 문서의 성격과 독자의 후속 행동을 기준으로 확정형/잠정형 표현을 구분하라.
- 배포 플랜, 운영 절차, 회의 결정사항, 실행 계획처럼 실행 기준을 제공하는 문서는 확인된 날짜, 버전, 담당자, 대상, 절차를 확정형으로 서술하라.
  - 예: `배포 버전은 1.1.0-RELEASE다`
  - 피하라: `1.1.0-RELEASE를 생성할 예정`, `후보`, `예상`
- 초안, 제안서, 비교 검토, 미확정 정책처럼 결정 전 문서는 잠정형 표현을 사용할 수 있다.
  - 예: `후보는 A/B다`, `확인이 필요하다`, `리스크로 보인다`
- `무너진다`, `흔들린다`처럼 원인과 영향을 흐리는 AI식 비유 표현은 자제하고, 실제 리스크와 영향을 구체적으로 서술하라.

# 구현 모드

코드 작성, 파일 수정 시 적용하라.

## 전제 조건
- 사용자의 명시적 승인을 받은 후에만 진입하라

## 코드 품질
- 컴파일되지 않는 코드를 커밋하지 마라
- 사용하지 않는 import, 변수, 메서드는 즉시 삭제하라
- .env, 인증 정보 등 보안 민감 파일은 커밋하지 마라
- 새 코드를 작성하기 전에 코드베이스의 기존 구현 → 표준 라이브러리·플랫폼 기능 → 설치된 의존성 순으로 재사용할 수 있는지 확인하고, 요구사항을 완전히 만족하는 것이 없을 때만 새로 작성하라
  - 같은 역할의 프로젝트 자체 구현이 있으면 표준 라이브러리보다 우선하고, 주변 코드가 쓰는 방식 그대로 사용하라
  - 몇 줄로 해결되는 기능 때문에 새 의존성을 추가하지 마라
- API 또는 도메인 필드명을 새로 정의하기 전에 기존 코드베이스와 API 계약에서 사용 중인 명칭이 있는지 먼저 확인하라
- 코드만 보고 의미를 알 수 없는 숫자·문자열(정책 값, 한도, 타임아웃, 외부 코드 값 등)은 이름 있는 상수로 정의하라
- 값만 봐도 의미가 분명한 리터럴(0, 1, -1, 빈 문자열, 인덱스, 단위가 드러나는 표현 등)은 상수로 빼지 마라
- 같은 의미의 값이나 용어가 세 곳 이상에서 쓰이면 하나의 상수로 통합하라
- 상수는 사용 범위에 가장 가까운 곳에 정의하고, 사용처가 한 모듈뿐이면 공통 상수 파일로 올리지 마라
- 정해진 값 집합(상태, 유형, 코드)은 문자열 상수로 흩어 두지 말고, 같은 개념의 기존 enum을 먼저 찾아 재사용하고 없을 때만 새로 정의하라
  - 이름이 같아도 외부 API 계약용 enum과 내부 도메인 enum은 합치지 말고 변환 계층에서 매핑하라
- 엔티티 상태를 `entity.getStatus() == Status.X`처럼 외부에서 꺼내 비교하지 말고, 의도를 드러내는 도메인 메서드(`isPaid()`, `canRefund()` 등)를 정의해 사용하라
  - 여러 상태를 묶는 조건은 상태 이름이 아니라 비즈니스 의미로 이름 지어라

## 주석
- 주석은 최소화하고, why만 남겨라
- TODO, FIX 주석에는 날짜와 작성자를 포함하라

## 커밋
- 커밋 메시지는 한글로 작성하라
- 형식: `<type>: <subject>` (예: `feat: 사용자 인증 기능 추가`)
- type: feat, fix, refactor, docs, test, chore
- 다중 파일 변경 시 squash 워크플로우를 따르라
  1. 구현 중에는 논리 단위마다 개별 커밋하라
  2. 완료 후 squash 하여 단일 커밋으로 합쳐라

# 검증 모드

테스트, 리뷰, 디버깅, 에러 대응 시 적용하라.

## 코드 리뷰
- 코드 품질, 보안, 비즈니스 무결성, 데이터베이스 네 가지 측면으로 검토하라
- GitHub PR 리뷰 코멘트를 반영하거나 반박할 때는 각 스레드에 답변을 남기고, 처리가 끝난 스레드는 resolve 하라
- 변경된 메서드의 호출부(caller) 전체 실행 흐름을 추적하라. 특히 검증/가드 조건이 완화된 경우, 호출부에서 검증 통과 후 핵심 로직 전에 무조건 실행되는 부수효과(카운트, 수수료, 이벤트)가 새 케이스에서도 올바른지 반드시 확인하라.
- 피드백에는 카테고리 태그와 심각도를 표기하라
  - 카테고리: [품질], [보안], [비즈니스], [DB]
  - 심각도: 경고 / 주의 / 사소
  - 예: [보안/경고] SQL 인젝션 가능성 있음

## 테스트
- 테스트 비활성화는 사용자의 명시적 승인 후에만 진행하라
- 모든 메서드에 테스트를 작성하는 대신, 실패 위험을 의미 있게 줄이는 테스트를 작성하라
- 불필요한 테스트를 만들지 말고, 동일한 역할을 하는 테스트는 통합하라
- 실제 결함을 잡지 못하는 커버리지용 테스트는 제거하라
- 모든 협력 객체를 Mock으로 격리하지 말고, 빠르고 결정적인 객체는 실제 객체를 함께 사용하라
- Mock은 느리거나 비결정적인 의존성(외부 API, 메시지 브로커, 시간, 난수 등)에만 사용하라
- 내부 호출 순서가 아니라 외부에서 관찰 가능한 결과(반환값, 상태 변경)와 계약을 검증하라
  - 단, 외부 상태를 바꾸는 호출(이벤트 발행, 결제·전송 요청)은 호출 자체가 계약이므로 보낸 내용을 검증하라
- 테스트 기대값에는 프로덕션 상수를 재사용하지 말고 리터럴을 사용하라

## 디버깅 및 에러 대응
- 근본 원인을 파악하기 전까지 코드를 수정하지 마라
- 가설을 먼저 세우고, 검증한 후 수정하라
- 에러 메시지와 스택트레이스를 먼저 읽고, 근본 원인을 파악하라
- 동일 명령을 무작정 재시도하지 마라
- 해결이 안 되면 사용자에게 상황을 보고하고 대안을 제시하라

# 도구 사용

## 정보 조회 우선순위
1. 외부 서비스는 MCP 도구를 우선 사용하고, 불가 시 API를 직접 호출하라
2. 코드베이스 탐색은 grep/rg 등으로 직접 수행하고, 복잡한 탐색은 Explore agent를 사용하라

## 버전 및 호환성
- 라이브러리 버전 선택, 외부 API/기능 사용 시 현재 날짜 기준 최신 정보를 확인하고 적용하라
- 라이브러리 설치/업그레이드 시 기존 의존성과 호환되는지 확인한 후 적용하라

## 병렬화 전략

### 탐색 및 리서치
- 독립된 조사 영역이 여러 개이고 각 영역에 3회 이상 쿼리가 필요한 깊은 탐색이면 서브에이전트로 병렬 조사하라. 한 영역의 결과가 다른 영역의 조사 방향을 정하면 순서대로 진행하라.
- 단순 검색(grep/rg, 파일 목록 조회)으로 해결되는 탐색은 직접 수행하라.

### 구현 작업
- 구현 계획의 태스크들을 분석하여 독립성을 판단하라. 다음 조건을 모두 만족하면 병렬 실행하라:
  1. 서로 다른 파일을 수정함
  2. 서로의 결과에 의존하지 않음
  3. 공유 상태(DB 스키마, 공통 모듈 등)를 동시에 변경하지 않음
- 태스크 간 의존성이 있더라도 인터페이스(API 스펙, 타입 정의, 프로토콜 등)를 먼저 정의하면 병렬화할 수 있다. 의존 관계가 보이면 다음 순서를 따르라:
  1. 공유 인터페이스를 먼저 정의하라 (API 스펙, 타입, 스키마 등)
  2. 각 태스크가 정의된 인터페이스에 맞춰 독립적으로 구현하도록 병렬 디스패치하라
- 독립성이 불확실하면 사용자에게 확인하라

# Subagent Driven 동작

- subagent-driven development 중 구현 단위별 중간 리뷰는 superpowers 기본 동작을 따른다
- 중간 리뷰에서 [품질], [보안], [비즈니스], [DB] 네 가지 관점 리뷰를 반복하지 않는다
- [품질], [보안], [비즈니스], [DB] 네 가지 관점 리뷰는 최종 완료 전 전체 구현 리뷰 단계에서만 수행한다
- 단, 구현 중 명백한 결함, 보안 위험, 비즈니스 무결성 훼손 가능성을 발견하면 즉시 작업을 멈추고 사용자에게 보고한다
